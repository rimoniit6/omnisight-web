# PHASE 2 REPORT — SCREENSHOT STORAGE, PROCESSING, THUMBNAIL & COST-CONTROL HARDENING

Status: **GREEN**
Date: 2026-09-03 (working tree, Phase 0/1 baseline intact, all changes uncommitted)

---

## 1. Executive Summary

Phase 2 was implemented as a fully additive hardening layer over the existing
screenshot pipeline. The original screenshot remains the single source of
truth; storage still goes through the one existing abstraction; the upload path
performs no image work; thumbnails are generated by a bounded, idempotent,
restart-safe background worker under the existing JobRun lease; retention
purges original + thumbnail together; the admin viewer is thumbnail-first; and
per-org byte accounting now includes thumbnails without counter tables.
**Zero agent changes.** No Phase 0/1 behavior, endpoint, field, or storage
contract was altered. Full web + agent regression gates pass.

## 2. Architecture Before

Documented in `docs/PHASE-2-BASELINE.md` (verified against the working tree):
upload wrote original object + Screenshot row synchronously (PNG dims only),
no thumbnail columns/job, admin grid/list fetched full-resolution originals,
retention/orphan-sweep knew only `filePath`, stats summed only `fileSize`, no
status machine.

## 3. Architecture After

Documented in `docs/PHASE-2-IMPLEMENTATION.md`. Upload leaves the row
`processingStatus='uploaded'` (DB default — the state IS the queue); the
`screenshot_processing` job (existing `claimJob` lease) drains oldest-first in
bounded batches, generates a ≤320px thumbnail via sharp through the existing
storage driver, and transitions the row to `processed`/`processing_failed`.

## 4. Database Changes (additive migration)

`prisma/migrations/20260903010000_screenshot_thumbnail_processing/`

- Columns on `Screenshot`: `processingStatus TEXT NOT NULL DEFAULT 'uploaded'`,
  `processingAttempts INT NOT NULL DEFAULT 0`, `processingError TEXT?`,
  `processedAt TIMESTAMP?`, `thumbnailPath TEXT?`, `thumbnailSize INT?`.
- Indexes: `(processingStatus, capturedAt)` (worker drain),
  `(organizationId, processingStatus)` (per-org status queries).
- Existing rows default to `uploaded` (bounded worker backfills thumbnails for
  pre-existing captures within the retention window). No existing data
  rewritten/dropped.

Evidence:

```
migrate deploy (fresh scratch DB)            → all 38 migrations applied
prisma migrate diff (applied DB → schema)    → "No difference detected."
```

## 5. Worker / Retry / Thumbnail Policy

- Constants centralized in `src/lib/screenshots/processing.ts`:
  `SCREENSHOT_THUMBNAIL_MAX_DIMENSION = 320`, quality 80,
  `MAX_SCREENSHOT_PROCESSING_ATTEMPTS = 3`, per-run default limit 100 (hard
  ceiling 500). No client-controllable dimensions.
- Never upscales (`withoutEnlargement`), preserves aspect (`fit: 'inside'`),
  honors EXIF, keeps source format, `limitInputPixels` 64 MP
  (decompression-bomb guard).
- Idempotent: deterministic key `<name>.thumb.<ext>`; in-flight state not
  persisted → crash leaves row `uploaded`, re-run overwrites the same object,
  never duplicates. `processed` rows excluded from the drain.
- Failure isolation: original always preserved; corrupt images bounded-retry →
  `processing_failed` with sanitized `decode_failed`; missing original fails
  permanently on first contact (`original_missing`).

Evidence (tests P2-02…P2-07): 320×200 thumb from 640×400 source; 100×80 source
stays 100×80; re-run after `processed` creates 0 duplicates; corrupt PNG fails
after exactly 3 attempts with `processingError='decode_failed'` and original
bytes intact; missing-original row → `processing_failed` while a healthy row in
the same batch succeeds.

## 6. API / Serving Changes

- `POST /api/agent/screenshot`: request/response contract unchanged; row now
  created with `processingStatus:'uploaded'` (explicit). No sync image work.
- NEW `GET /api/screenshots/[id]/thumbnail`: identical authorization to the
  original image route (session auth, org-scoped 404 concealment, magic-byte
  Content-Type, `nosniff`), `Cache-Control: private, max-age=86400`
  (deterministic objects), 404 when no thumbnail exists.
- `GET /api/screenshots/stats`: additive `thumbnailStorage` (sum of
  `thumbnailSize`); `totalStorage` semantics unchanged.
- `DELETE /api/screenshots/[id]`: deletes thumbnail + original + row.

Evidence (P2-08…P2-09, P2-11, P2-12): thumbnail 200 with correct headers;
unprocessed row → 404; cross-org → 404; unauth → 401; DELETE removes both
physical objects; stats `thumbnailStorage` equals the derived DB sum while
`totalStorage` keeps original-byte semantics.

## 7. Retention / Orphan Handling

`src/lib/jobs/retention.ts` + `src/lib/screenshots/sweep.ts` (same scheduler):
- Purge deletes thumbnail FIRST then original; DB row deleted only when BOTH
  artifacts are confirmed gone (file-first, retry-safe, org-scoped).
- Orphan sweep references `thumbnailPath` basenames so processed thumbs are
  never swept; orphaned thumbs are swept like orphaned originals.

Evidence (P2-10, P2-13): stale processed row → original + thumb files gone and
row gone; fresh row + thumb survive; org B untouched by org A's run; bounded
purge ≤ limit on the 10k dataset.

## 8. Admin UI

`src/components/screenshots/screenshots-page.tsx`: grid cards and list-view
previews load `[id]/thumbnail` first (when `processed`), fall back to the
authorized original, then to the existing placeholder. The viewer modal still
loads the full-resolution original on demand ("click → authorized original").
No synchronous generation from the browser.

## 9. Security & Privacy Verification

- Thumbnail access: same `requireSessionOrg` + org-scoped lookup as originals;
  cross-org and org-less-super-admin reads concealed (404); tests P2-09.
- Upload-path auth/consent/size/magic-byte checks untouched (existing
  `tests/screenshots.test.ts` 40/40 green).
- No new data collection; no keystroke/email/audio/webcam changes; consent and
  fail-closed behavior unchanged (Phase 2 hardens an existing feature only).
- `processingError` stores sanitized categories only — no paths/stack/secrets.

## 10. Performance / Volume

Evidence (P2-13, 10,000 synthetic rows, dedicated org):
- Worker drains exactly its per-run limit (100), remainder stays queued;
  missing-object rows fail fast with no sharp work (250/250 bounded).
- Retention purges at most its per-run limit (500).
- List API stays org-scoped/correct on 10k rows (24/page, page 3, bounded
  response); org B and org A totals isolated.
- Upload never waits for processing: the request performs zero image work
  (P2-01 asserts `processingStatus='uploaded'`, no thumbnail, at request end;
  P2-14 asserts the unchanged response contract).
- Throughput: default 100 rows/run at a 60 s cadence (min 15 s) ≈ 100/min
  capacity against a ~23/min sustained rate at 1 M/month scale; each decode is
  bounded to ≤5 MB input / 64 MP decode / 320px output with per-row sequential
  processing.

## 14. Rollback

1. Stop the worker (env interval / instrumentation block / previous build) —
   originals and the original-image route are unaffected; the UI falls back to
   original images automatically.
2. Revert additive code; keep or drop the additive migration as desired (all
   new columns are nullable/defaulted and inert without the worker).
3. Never delete original objects as part of rollback.

## 15. Remaining Risks / Warnings

- Supabase Storage has no orphan-object sweep (pre-existing, documented in
  `sweep.ts`); orphan cleanup there remains driver-level (every write/delete
  already goes through the driver).
- The worker adds bounded CPU on the app process (≤100 sharp ops/run at 60 s);
  heavy deployments can tune `SCREENSHOT_PROCESSING_INTERVAL_SECONDS` or the
  per-run limit.
- Offline/dev databases with pre-existing rows whose physical files are absent
  will see those rows transition to `processing_failed` (`original_missing`) —
  correct, bounded, and non-destructive.
- Lint warnings remain at the pre-Phase-2 count (439, all pre-existing); Phase
  2 code added 0 errors and 0 new warnings.
