## 2. SQLite-Specific Code Inventory (verified, line-level)

### 2.1 Schema-level
- `prisma/schema.prisma`: `provider = "sqlite"` — the single provider declaration.
- No `@db.` type annotations, no `BigInt`, no `Decimal`, no `Json` fields (JSON is stored as `String?`), no `Bytes`.
- All IDs are `String @id @default(cuid())` — **portable to PostgreSQL unchanged**. All FK/unique/index declarations are standard Prisma DDL and translate cleanly.
- `onDelete: Cascade / SetNull / Restrict` — portable.
- **No SQLite-only constructs** (e.g., `AUTOINCREMENT`, `INTEGER PRIMARY KEY`, `PRAGMA`) exist in the schema.

### 2.2 Migration files (29 folders)
SQLite-dialect SQL throughout — examples observed:
- `PRAGMA` statements in several migrations (`migrations/20260802152439_m004_*` etc.).
- `AUTOINCREMENT` / `INTEGER PRIMARY KEY` style DDL where present.
- SQLite type names (`TEXT`, `INTEGER`, `REAL`, `DATETIME`).

**Decision:** SQLite migration SQL is not executable on PostgreSQL. There is **no existing PostgreSQL data** to preserve (the `workai` database does not exist yet). The correct, standard Prisma procedure is a **consolidated PostgreSQL baseline migration** reflecting the current schema (the logical end-state of the 29 SQLite migrations). The 29 SQLite migrations are **archived** (moved to `prisma/migrations-sqlite-archive/`, git-tracked) — never deleted — preserving the full logical history. `migration_lock.toml` is regenerated by Prisma with `provider = "postgresql"`.

### 2.3 Case-insensitive search — REGRESSION RISK (must fix)
SQLite's `LIKE` is case-insensitive for ASCII; PostgreSQL's `LIKE` is **case-sensitive**. The following routes rely on SQLite's implicit behavior via `{ contains: q }` **without** `mode: 'insensitive'`:

| File | Pattern | Fix required |
|---|---|---|
| `src/app/api/employees/search/route.ts` | `{ [field]: { contains: token } }` | add `mode: 'insensitive'` |
| `src/app/api/search/route.ts` | `contains` on employee/department/device name fields (+ JS filter) | add `mode: 'insensitive'` |
| `src/app/api/projects/route.ts` | `where.name = { contains: search }` | add `mode: 'insensitive'` |
| `src/app/api/projects/search/route.ts` | `{ name: { contains: token } }, { id: { contains: token } }` | add `mode: 'insensitive'` |
| `src/app/api/sentiment/route.ts` | `contains` on employee first/last/employeeId | add `mode: 'insensitive'` |
| `src/app/api/auth/users/route.ts` | `where.email = { contains: search }` | add `mode: 'insensitive'` |
| `src/app/api/auth/login/route.ts` | two-step email lookup (lowercase exact, then scan fallback) | single `equals` + `mode: 'insensitive'` |
| `src/app/api/projects/[id]/route.ts` | duplicate-name check (fetch + `toLowerCase()` in JS) | works on PG as-is; comment refresh only |

PostgreSQL natively supports `mode: 'insensitive'` (`ILIKE`), so these become **server-side, database-driven case-insensitive searches** — the correct long-term fix, not a workaround.

### 2.4 Raw SQL audit (G9)
`src/app/api/screenshots/ocr-search/route.ts`:
- `$queryRawUnsafe` × 2 — **parameterized** (`?` placeholders), no string interpolation of user input.
- Syntax used (`LOWER()`, `LIKE`, `LIMIT ? OFFSET ?`, `COUNT(*)`, quoted identifiers) is **valid PostgreSQL**.
- `COUNT(*)` returns `bigint` on PG — already handled via `Number(...)`.
- `%`/`_` escaping uses backslash — PostgreSQL's default `LIKE` escape character is backslash → compatible.
- **Verdict: safe to run on PG unchanged. Do NOT replace (rule: don't replace safe raw SQL).**

## 6. Data Migration Plan (G4)

SQLite → PG via `scripts/migrate-sqlite-to-postgres.mjs`:
1. Read `db/custom.db` read-only (`node:sqlite`).
2. Write to PG with parameterized `INSERT` (`$1..$n` via Prisma `$executeRawUnsafe`) — all values passed as text and cast by PostgreSQL per column type (int/float/bool/timestamptz/text all accept text input).
3. Explicit type conversion for **DateTime columns** (ISO-8601 UTC normalization — SQLite Prisma dates are UTC) and **Boolean columns** (0/1 → `0`/`1`, accepted by PG boolean).
4. FK-safe insert order; `Department.managerId` circular ref resolved by two-phase insert.
5. Validation: per-table row counts (SQLite vs PG), FK-orphan queries, unique-constraint status, representative app queries.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Prisma 6.11.1 vs PostgreSQL 18 | Direct `migrate deploy` test on fresh DB; fallback documented (pin PG ≤17 or upgrade Prisma) |
| Case-insensitive search regression | `mode: 'insensitive'` added to all `contains` sites (2.3) |
| Date/timestamp semantics | ISO-8601 UTC normalization in migration script; Prisma writes UTC on both providers |
| `db push` vs production rule | `db push` only for throwaway test DBs; production path is `prisma migrate deploy` (verified) |
| Data loss | SQLite file + `.bak-*` copies preserved until PG is validated; row-count + FK validation gates |
| Secret leakage | `JWT_SECRET`/passwords never printed or committed; `.env` gitignored; `.env.example` placeholders only |
