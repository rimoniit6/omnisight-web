## 3. Commands Executed (chronological)

```bash
# 1. Inspect: confirm no migrations exist, identify real DB & decoy
ls prisma/                        # no migrations/ folder → db push workflow
grep DATABASE_URL .env            # file:../db/custom.db  (real DB = db/custom.db)
echo "$DATABASE_URL"              # ⚠ shell exports file:./db/custom.db → decoy (prisma/db/custom.db)

# 2. Safety: verify DB↔schema parity (must be empty diff)
env -u DATABASE_URL npx prisma migrate diff \
  --from-schema-datasource=prisma/schema.prisma \
  --to-schema-datamodel=prisma/schema.prisma --script
#   → "This is an empty migration."  (DB fully in sync with schema)

# 3. Backup (both DBs)
cp db/custom.db db/custom.db.bak-m001
cp prisma/db/custom.db prisma/db/custom.db.bak-m001

# 4. Generate baseline SQL (from empty → schema)
mkdir -p prisma/migrations/0001_init
env -u DATABASE_URL npx prisma migrate diff \
  --from-empty --to-schema-datamodel=prisma/schema.prisma --script \
  > prisma/migrations/0001_init/migration.sql

# 5. Migration lock file
#   (created prisma/migrations/migration_lock.toml with provider = "sqlite")

# 6. Mark baseline as applied WITHOUT executing (tables already exist)
env -u DATABASE_URL npx prisma migrate resolve --applied 0001_init
#   → "Migration 0001_init marked as applied."

# 7. Verify
env -u DATABASE_URL npx prisma migrate status
#   → "1 migration found ... Database schema is up to date!"

# 8. Scripts + client + build
npm run db:generate   # ✔ Prisma Client generated
npm run build         # ✔ Next.js build + standalone copy
```

> ⚠ **Critical note on `env -u DATABASE_URL`:** the shell exports `DATABASE_URL=file:./db/custom.db`, which Prisma resolves **relative to `prisma/schema.prisma`** → `prisma/db/custom.db` (the **decoy** empty DB from the P2021 incident). `.env` correctly declares `file:../db/custom.db` → the real `db/custom.db`. Shell env vars override `.env`, so every Prisma CLI invocation in this environment must use `env -u DATABASE_URL` (or unset the variable) to avoid operating on the wrong database.

## 6. Known Limitations

1. **Shell `DATABASE_URL` hazard** (see §3): any Prisma command run *without* `env -u DATABASE_URL` in this shell targets the decoy `prisma/db/custom.db`. Recommend `unset DATABASE_URL` in the dev shell or fix the exported value to `file:../db/custom.db`.
2. **`db:push`/`db:reset` scripts remain** in `package.json` — kept for scratch/demo use only. After M001, the canonical workflows are `db:migrate` (dev) and `db:deploy` (production). `db:push`/`db:reset` must **not** be run against buyer data.
3. **`migrate dev` on a fresh clone:** a developer cloning the repo with an existing `db/custom.db` created via `db push` would see drift; the documented path is `prisma migrate deploy` (which no-ops because `0001_init` is already recorded) — or delete the DB and run `migrate dev` to recreate + seed.
4. **Windows file locks:** a running `next dev` process locks `query_engine-windows.dll.node`, breaking `prisma generate`. Stop dev servers before running `db:generate` (hit during this task; resolved by killing PID 4768).
5. Baseline migration is generated from `--from-empty`, so it represents a **fresh** database. It was marked applied rather than executed — this is the correct and standard baseline technique for adopting Prisma Migrate on an existing DB.
6. **`db:push` / `db:reset`** remain destructive; they are **not** the canonical workflow after M001 — remove or gate them before the v1.0 release.
