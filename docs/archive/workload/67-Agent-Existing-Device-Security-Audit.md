# Phase 3 Security Hardening — STEP 1: Agent Existing-Device Rediscovery Audit

> **Scope:** READ-ONLY audit. No source code was modified.
> **Date:** 2026-08-11
> **Objective:** Document the authenticated AgentSession → existing-device rediscovery flow, locate the cross-org / wrong-employee authorization gap, and define the security rules for the fix (STEP 2+).
> **Verdict:** Vulnerability CONFIRMED in `src/app/api/agent/discover/route.ts` — the existing-device branch trusts the Device row as identity authority instead of the authenticated AgentSession.

---

## 1. Flow trace (complete)

### 1.1 How AgentSession identifies the employee

`src/lib/agent/session.ts` — `validateAgentSession(req)`:

- Reads `Authorization: Bearer <token>`, requires ≥ 20 chars.
- Looks up `AgentSession` by token (`db.agentSession.findUnique({ where: { token } })`).
- Checks `expiresAt` (24h TTL), then re-loads the **live** `Employee` by `session.employeeId` (must exist, `status === 'active'`), the live `AgentAccount` for that employee (`status === 'active'` — admin-disable fails closed mid-session), and the live `Organization` (`status === 'active'`).
- Returns `employee: { id, employeeId, firstName, lastName, organizationId, status }` — all **server-derived from DB rows**, never from the request.
- Single `valid:false` shape for every failure — no reason leakage.

### 1.2 How AgentSession identifies organizationId

`session.organizationId` is **denormalized at login time** from `AgentAccount → Employee.organizationId` (`createAgentSession` in session.ts; the login route passes `employeeRecord.organizationId`, which came from `verifyAgentCredential` → `employee.organizationId`). It is:
- Never accepted from the login body (login destructures only `agentId` + `password`).
- Re-validated live at every session validation against the current `Organization.status`.
- Cross-checked against the live Employee row at validation (`employee.organizationId`), so an org move invalidates the session's org authority.

### 1.3 How deviceKey is resolved

`discover/route.ts` line 97:

```ts
const device = await db.device.findFirst({ where: { agentKey: deviceKey } });
```

- `deviceKey` is client-supplied (16–128 chars) — a machine identity generated by the desktop agent.
- The lookup is **GLOBAL** — NOT scoped by `organizationId` or by the authenticated session.
- `Device.agentKey` has a unique constraint (`@unique`), so `findFirst` returns at most one row.

### 1.4 What happens when the device already exists

The transaction at lines 174–264 (`SELECT id FROM "Device" WHERE id = ${device.id} FOR UPDATE`, then latest-claim state machine):

| Latest claim state | Response |
|---|---|
| `approved` | `{ status: 'approved', employeeAssigned }` — no new secret |
| `pending` (unexpired) | `{ status: 'pending', claimId }` — idempotent, no new secret |
| `revoked` | `{ status: 'revoked' }` — terminal, fail closed |
| `rejected` (no `reRegister` intent) | `{ status: 'rejected' }` — surfaces rejection |
| `pending` expired / `cancelled` / `rejected` + `reRegister` | close old, create **FRESH** claim with `organizationId: device.organizationId` (line 219) + new one-time secret |

**CRITICAL: this branch performs NO authorization check against the authenticated session.** If a valid AgentSession is present, the existing-device branch never compares `device.organizationId`/`device.employeeId` with `session.organizationId`/`session.employeeId`. The Device row — which may belong to another employee or another organization — becomes the authority for all subsequent behavior (claim creation, org attribution, status disclosure).

### 1.5 What happens when the device is unassigned

- **New-device path** (line 104): when authenticated, the device is created with `employeeId: authenticatedEmployee.id` and `organizationId: org.id` (session org). Correct.
- **Existing-device path** (line 174+): `device.employeeId === null` is **never handled**. The device stays unbound; a fresh claim (if one is issued) is created under `device.organizationId` with no employee link. The authenticated employee's identity is NOT applied, and no rebind occurs. Rule D (safe assignment) is unimplemented.

### 1.6 What happens when the device belongs to another employee (same org)

**No check.** Employee A (valid session, org X) rediscovering Employee B's device (org X) receives B's device claim state, `deviceId`, `claimId`, `employeeAssigned` — full disclosure of another employee's device registration state, and (for cancelled/expired/rejected + reRegister) creates a fresh claim against B's device under org X. Employee A can also observe B's device's pending status and cancellation transitions. Rule B (safe denial) is unimplemented.

### 1.7 What happens when the device belongs to another organization

**No check.** Agent A (org X) rediscovering org Y's device:
- Reads org Y's device row and claim state; the response leaks `deviceId`, `claimId`, `status` (approved/pending/revoked/rejected), `employeeAssigned`.
- On the fresh-claim path, creates a **new PENDING DeviceClaim in org Y** (line 219: `organizationId: device.organizationId`), polluting org Y's admin approval queue from an org X session. Audit/notification attribution: the existing-device path writes audit logs keyed to `device.organizationId` without the employee — an unattributed, unauthorized claim in another tenant.
- Rule C (block + conceal) is unimplemented.

### 1.8 What happens when the device is revoked/disabled

- `revoked` latest claim → `{ status: 'revoked' }` returned **to whoever supplies the deviceKey** — same-org owner, wrong employee, or cross-org session alike. No authorization.
- Device `status: 'inactive'` (disabled/deactivated): discover has no device-status gate of its own (only `validateAgentToken` enforces device status on device routes). An inactive device with an approved claim returns `approved` + `employeeAssigned` — the terminal-device state check for "disabled" is entirely absent in the existing-device branch.

### 1.9 What happens when a previously approved device reconnects

Latest claim `approved` → `{ status: 'approved', employeeAssigned: device.employeeId !== null }`. No token is issued by discover (PATH A authenticate does that with the one-time claim secret). For the owning employee this is correct; for any other session (wrong employee / wrong org) it discloses the approved state — same Rule B/C gap.

### 1.10 What happens for anonymous zero-touch discovery

No valid AgentSession → `authenticatedEmployee = null` → org = `db.organization.findFirst({ orderBy: { createdAt: 'asc' } })` (single-tenant fallback, unchanged legacy behavior):
- New device created **without** employee binding (admin assigns at approval).
- Existing-device branch behaves as today with no session authority — the Device row drives everything. This path must remain byte-for-byte compatible (Rule E).

## 2. Request-body client-control assessment

`discover/route.ts` lines 30–45 destructure ONLY: `deviceKey, hostname, os, osVersion, processor, memory, agentVersion, arch, reRegister`.

**`employeeId` and `organizationId` are NOT read from the body today** — there is nothing to "remove". AUTH-EXIST-04/05 therefore reduce to regression tests proving body-supplied values (if an attacker adds them) are ignored, plus the real fix: the Device **row** must no longer act as identity authority for authenticated requests.

---

## 3. Root cause (single statement)

> The existing-device branch of `POST /api/agent/discover` performs its state machine against the **Device row** (`device.organizationId`, `device.employeeId`, latest claim) without first verifying that the row's organization and employee match the authenticated AgentSession's server-derived identity — so a valid session can read, and in the fresh-claim path mutate, device state belonging to another employee or another tenant.

Contributing factors:
1. Global `agentKey` lookup, not scoped to the session org (1.3).
2. No org check before returning device state (1.7).
3. No employee-ownership check for same-org devices (1.6).
4. Unassigned-device rebind absent on the existing-device path (1.5).
5. Fresh claims minted under `device.organizationId` regardless of session (1.4).
6. Response bodies expose `deviceId`/`claimId`/`status`/`employeeAssigned` unconditionally (1.6/1.7/1.8).

## 4. Security rules to enforce (STEP 2 contract)

| Rule | Condition | Action |
|---|---|---|
| A | `device.organizationId === session.organizationId && device.employeeId === session.employeeId` | Allow; existing state-machine behavior |
| B | Same org, `device.employeeId !== session.employeeId` (non-null) | **404 safe concealment** — no reassign, no disclosure |
| C | `device.organizationId !== session.organizationId` | **404 safe concealment** — never operate on the device |
| D | Same org, `device.employeeId === null` | **Transactional bind** `employeeId = session.employeeId` inside the device row lock |
| E | No valid session | Preserve anonymous zero-touch byte-for-byte |

The 404 body must be identical to the route's existing "not found" shape (`{ error: 'Device not found' }`), never containing: device/claim ids, status, employee/org names, `employeeAssigned`.

---

## 5. Concurrency plan (STEP 4)

- The authorization check + optional Rule-D bind must execute **inside** the existing `SELECT ... FOR UPDATE` transaction (device row lock) so two racing discoveries from different sessions serialize: second txn re-reads the locked row, sees the bind from the first, and applies Rule A/B/C against the final state.
- No new schema change needed: `Device.employeeId` + `organizationId` already exist; binding is a plain update.
- No Prisma migration required (`Device`, `DeviceClaim`, `AgentSession` unchanged).

---

## 6. Residual risks after the fix (to carry into STEP 8)

1. **Enumeration distinguishability:** for a valid session, an unknown `deviceKey` currently triggers device creation (201); after the fix a cross-org/wrong-employee existing key returns 404. A probing agent can therefore distinguish "new key" from "existing key owned elsewhere" by status-code difference. Accepted per STEP 2 (the prompt mandates 404); the attacker gains no row content — only existence-in-another-tenant, and only while holding a valid AgentSession for their own tenant.
2. Legacy PATH B (`/api/agent/authenticate` + `Employee.agentPassword`) — unrelated pre-existing scope; unchanged.
3. `device.status` gates on the discover route (inactive-device reconnect) — see 1.8; consider aligning with `validateAgentToken` semantics, but NOT required by the AUTH-EXIST contract (AUTH-EXIST-11 is covered by the revoked-claim path and 404 rules).
