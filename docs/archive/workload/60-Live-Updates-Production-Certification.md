## 1. Code audit (mini-services/live-updates/index.ts)

- Auth: JWT verified on handshake (`auth.token`) OR the httpOnly session cookie; invalid/expired → disconnect.
- Isolation: each socket joins `org:<organizationId>`; broadcasts are room-scoped → no cross-tenant leakage.
- Data: events generated by polling the DB for real changes; the service never writes.
- Port: `LIVE_UPDATES_PORT` (3010 default), proxied by Caddy only when `?XTransformPort=3010` (fixed allowlist).

## 2. Admin client (websocket-provider.tsx)

- Connect `io('/?XTransformPort=3010', { transports:['websocket','polling'], reconnection:true, reconnectionAttempts:20, reconnectionDelay:2000→10000 })`.
- `connect_error` handling: stops retrying on auth failure; marks disconnected.
- **Degrade path:** `devices-page.tsx` uses `useLiveUpdates()` → `isConnected`; when live updates are off/disconnected it falls back to 15s `refetchInterval` polling. WS failure does NOT break admin functionality. ✅

## 3. Required live verification (post-deployment)

1. WSS upgrade over HTTPS (Caddy → 3010)
2. Two admin clients in the same org both receive device-status events
3. Reconnect after server restart; disconnect recovery
4. Cross-org isolation test (client B never receives org A events)
5. Degrade check: stop WS → admin still works via polling

## 4. Conclusion

Service is secure by design and the admin degrades gracefully (P3, B-10). Live WSS verification is
a deployment task, **NOT VERIFIED** in this environment.
